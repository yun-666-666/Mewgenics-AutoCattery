# 家具分析与自动放置功能设计

更新日期：2026-08-09

状态：Stage 37 已确认玩家手动移动同一家具时存档只改变 `x/y`，并部署 F7
运行时双快照对象图探针。下一步用真实报告锁定选中家具对象与原生拿起/放置
接口；Anchor、完整禁放区、合法布局求解和自动执行仍未完成。

### 2026-08-09 Stage 31 实施校正

已完成 F01 的第一段只读基础，但尚未完成方向、旋转、稀有度和家具占地解码：

- 当前存档家具字符串头不是可直接赋予语义的 `u64 length`，而是
  `u32 length + u32 unknown`。当前样本的两个 unknown 均为 0；公开解析实现
  只作为交叉佐证，最终以当前 257 条记录完整消费为准。
- `furniture_info.data` 每行同样为 `u32 name_length + u32 unknown + name +
  580 opaque bytes`；当前 634 行的 unknown 均为 0，文件精确消费到 EOF。
- 家具记录内的 `u64 unknown_before_room` 当前有 0 和 2 两种值；尾部两个
  unknown 当前全为 `1,1`。没有足够证据把任一字段命名为旋转、翻转或稀有度。
- 当前 House 资源包含 11 个房间定义和 3 个 House 布局；布局位置数包含
  Basement，因此不能把资源中的 2/8/10 直接解释为玩家普通房间数。
- 合成回归已覆盖 1、2、3、5、7 房，证明解析与数据模型使用动态集合；真实
  1/2/3/5 房仍需要玩家存档或运行时只读探针分别验证。

### 2026-08-09 Stage 34 初始网格观察（已由 Stage 36 纠正）

- 当前 634 条 `furniture_info.data` 记录的 580 字节 payload 中，仅偏移
  `224..379` 出现非零值。Stage 34 将这 156 个连续 byte 直接解释成 12x13，
  后续当前 build 静态证据证明这是错误的行列解释。
- 当前所有网格值都在 `0..5`。结合当前资源的已知家具形状与公开家具编辑器的
  绘制说明，确认 0 Empty、1 Hitbox、2 Solid、3 Support、4 Surface、
  5 PoopLogic。
- Stage 34 的 tile 总数和三个存档覆盖率仍有效，因为当前所有非零 tile 恰好都
  落在该扁平区间内；但坐标形状与 `At(x,y)` 结果被 Stage 36 取代。

### 2026-08-09 Stage 35 Rare 标志校正

- 当前 `Mewgenics.exe` SHA-256 为
  `C3A41E436A93FA58CD386EC46DAD5C2A6F21A583D33C3A57A15A2604C726439E`。
- 当前创建路径 RVA `0x205090` 分配 `0x68` 字节家具记录并将 `+0x28` 清零；
  在资源键 `can_be_rare` 允许且调用方请求稀有时，对 `+0x28` 执行按位或 `2`。
- load/save 路径 RVA `0x22F7E0` / `0x230510` 均把该字段作为持久化 `u64`
  读写，因此 `0x2` 已确认是 Rare 标志，不是旋转或方向。
- 解析保留完整 `placement_flags`。当前只认识 `0x2`；未来出现任何其他位时，
  只把对应家具实例标记为 flags 不支持，不阻断其他实例的只读解析。
- 第 17、32 天分别 10/10、20/20 条 flags 支持且无 Rare；第 265 天 257/257
  条支持，其中 3 条为 Rare。三个存档全程只读。

### 2026-08-09 Stage 36 网格坐标与 scale 校正

- 家具初始化 RVA `0x2EBC80` 在取得 580 字节 payload 后明确 `+4`，随后创建
  24x24 byte 网格并复制完整 576 byte。当前 634 条记录的 4 字节头均为 0，
  全网格值均为 `0..5`，网格外非零记录为 0。
- 当前非零 tile 的实际 24x24 全局边界是 x=`7..15`、y=`9..15`。旧
  `224..379` 区间对应 24 列扁平网格的局部带状范围，不能作为 12 列换行。
- 存档尾部两个字段是有符号 `scale_x/scale_y`：加载时恢复到组件 double scale，
  保存时再取整写回。当前家具交互只找到水平符号翻转路径，未找到垂直翻转入口。
- 在保守支持的 `scale_x/scale_y = ±1` 下，当前 build 的加载和网格转换共同证明
  `room_x = position_x + scale_x * local_x`、
  `room_y = position_y + scale_y * local_y`。其他值按单件实例不支持处理。
- 房间运行时碰撞尺寸为资源 width/height 各加 2；无自定义矩阵时添加一格值 2
  边界，自定义 `built_in_collision` 必须为 `(height+2) x (width+2)`，并从资源
  顶到下行序翻转成运行时 y 轴。当前 11/11 房间定义均可只读解码。
- 第 17、32、265 天的全部 287 件现有家具 scale 仍全为 `(1,1)`。玩家确认当前
  家具没有旋转入口，因此 MVP 固定使用现有朝向，不再以翻转作为功能门槛。
- 7 猫存档的 `object_cattree1` 手动移动差分只改变 `x: -6 -> 3`、
  `y: -7 -> -9`；稳定实例 key、item、room、z、flags、scale 与其他 9 件家具
  均保持不变，证明保存坐标可作为原生移动读回条件。

### 2026-08-09 Stage 37 手动移动运行时探针

- Release 已部署 F7 双快照：进入家具界面后，第一次 F7 采集移动前
  `FurnitureBuildingUI` 与 House scene 两层对象图；手动移动并放下后第二次 F7
  采集差分。
- 报告只保留变化对象、父指针偏移、vtable RVA、变化字节区间及有界的
  `int32/double/pointer` 候选，不保存原始内存块。
- 该报告将直接用于识别选中家具组件、运行时 transform 和当前 build 的原生提交
  函数，随后实现单件 `FurniturePlacementGateway`。

这解决了家具基础网格尺寸、当前 `±1` scale 坐标变换和房间基础碰撞行列映射，
但尚未证明 Anchor、Background、门口、墙面、天花板、斜顶等碰撞值语义；原生
移动仍需 Stage 37 的运行时对象报告。合法布局和批量“自动放置”继续禁用。

## 1. 目标

在 House 家具界面保留两个由玩家主动点击的按钮：

- `开始分析`：读取当前存档、当前 House、所有已解锁房间、全部家具和当前猫房间
  规划，只生成分析与放置预览，不移动家具。
- `自动放置`：仅在存在有效分析结果时启用；玩家点击后，按照该预览通过当前
  游戏 build 的原生家具路径分批执行。

功能必须动态支持当前实际存在的任意房间数量，不得把算法写死为四房。明确验收
范围包括 1、2、3、4、5 房，并为未来出现的更多房间保留同一条通用路径。

本功能只整理家具和计算房间用途，不自动结束一天、休息、出征、组队、淘汰猫或
修改游戏原始文件。

## 2. 现有能力与缺口

当前仓库已经具备：

- 手动点击触发的 House 预览和二次确认工作流。
- 当前 build 的猫 `MoveOnly`、运行时刷新、计划失效检测和分批执行。
- 从存档 `furniture` 表读取家具 ID 与所属房间。
- 从 `resources.gpak/data/furniture_effects.gon` 读取 Comfort、Stimulation、
  Health、Mutation、Appeal。
- 从 `furniture_info.data` 保守读取 4 字节 opaque 头和完整 24x24 家具放置网格，
  包含 Empty、Hitbox、
  Solid、Support、Surface、PoopLogic 六种 tile。
- 从房间 width/height 合成一格边界，或将严格匹配的 `built_in_collision` 行序
  转成当前 build 的运行时碰撞网格。
- 从存档读取有符号 `scale_x/scale_y`，并对 `±1` 提供只读单元坐标变换。
- 玩家手动移动同一家具的前后存档只改变 `x/y`，可作为原生移动后的读回标准。
- 已部署 F7 家具运行时对象图差分探针。
- 根据猫、繁育组合和房间属性判断繁育、战斗驻留、育幼与普通用途。

尚未确认或实现：

- Stage 37 F7 报告中的选中家具对象、transform 字段和原生调用接缝。
- 房间碰撞 byte 的完整语义，以及门口、墙面、天花板和阁楼斜顶禁放规则。
- Anchor Point、Anchor、Background 约束。
- 当前 build 的原生家具拿起、移动、放下、回仓库和结果读回接口。
- 家具批量执行、反向计划、撤销和持久化后的玩家实机验证。

所有未知字段和函数都必须先通过只读探针确认，不得从文档、Wiki、名称或旧版本
偏移猜测。

## 3. 动态 N 房间模型

规划器的输入必须是运行时发现的 `available_rooms` 集合，其大小记为 `N`。房间
ID 只作为稳定身份，不用于硬编码用途；不得假设 Attic 永远是繁育房，也不得假设
Floor 编号代表属性或面积。

### 3.1 房间数量策略

| 房间数 | 规划原则 |
|---|---|
| 1 房 | 所有用途合并。先保证繁育安全底线和全体猫健康，再提高刺激；不能虚构独立战斗房或育幼房。 |
| 2 房 | 优先形成繁育房与安全综合房；战斗猫、幼猫和普通猫根据实际需求共享第二房，或在证据更优时交换用途。 |
| 3 房 | 通常可形成繁育、战斗驻留、育幼/恢复三类，但仍由猫群需求、家具和几何结果决定，不固定角色。 |
| 4 房 | 可增加普通储备、恢复或变异用途；不强制每个用途恰好一房。 |
| 5 房 | 允许繁育、战斗驻留、育幼、恢复/储备、变异等用途分离，也允许出现多个繁育房或多个普通房。 |
| N 大于 5 | 根据猫类别数量、繁育组合池规模、家具收益和房间几何动态决定每种用途需要 0、1 或多个房间。 |

房间多不代表必须创建更多用途。没有足够的合格繁育猫、幼猫或对应家具时，不应
为了填满角色表而制造空房或低质量专用房。

### 3.2 房间角色允许重复

角色分配不是一对一枚举，而是动态多重集合：

- `Breeding`：零个、一个或多个繁育房。
- `CombatStaging`：零个、一个或多个安全战斗猫驻留房。
- `Nursery`：没有幼猫时为零；幼猫多且房间充足时可以多个。
- `Recovery`：高健康、高舒适的老猫、伤病猫或安全驻留用途。
- `MutationLab`：只在繁育基础稳定或玩家主动开启后出现。
- `GeneralReserve`：承接其余猫和家具，可有多个。
- `FightClub`：默认永远为零；只有玩家明确开启并锁定用途后才参与。

每个角色数量由需求估算产生候选，再由联合优化器选择最终方案。

## 4. 房间属性目标

| 用途 | 主要目标 | 硬限制或风险 |
|---|---|---|
| 繁育房 | 平衡有效 Comfort 与 Stimulation；稳定全 7 后再比较 Mutation；Health 作为后续同分项 | 有效 Comfort `<= -10` 时繁育尝试自动失败；禁止 BreedSuppression 家具 |
| 战斗驻留房 | Health、Comfort，其次 Stimulation | 默认不是低舒适 Fight Club；禁止增加致死风险的特殊家具 |
| 育幼房 | Health、Comfort，其次 Stimulation | 不让幼猫承担实验性打斗或负健康环境 |
| 恢复房 | Health、Comfort | 避免负 Health、负 Comfort 和危险特殊效果 |
| 普通储备房 | 保持安全、可通行，并承接对专用房有害的家具 | 不得成为未知或危险家具的无条件倾倒区 |
| 变异房 | Comfort、Mutation，并保留满足阶段目标的 Stimulation | 未稳定繁育基础时不得抢占核心资源 |
| Fight Club | 低 Comfort | 可能受伤或死亡；必须玩家显式选择，不能由自动分析自行启用 |

Appeal 作用于全屋，不作为单房用途。分配 Appeal 家具时，应先满足专用房安全与
属性目标，再选择对其他目标伤害最小的合法位置。

有效 Comfort 必须包含猫数量影响。公开机制称每个房间超过四只猫后，每多一只
使 Comfort 降低 1，因此分析必须使用预计入住数量，而不是只显示家具原始总和。

## 5. 两按钮状态机

| 状态 | 开始分析 | 自动放置 |
|---|---|---|
| 未分析 | 可点击 | 禁用 |
| 分析中 | 显示“正在分析…”并禁用重复点击 | 禁用 |
| 预览可用 | 可重新分析 | 启用 |
| 预览失效 | 可点击 | 禁用并提示重新分析 |
| 执行中 | 禁用 | 显示批次进度 |
| 部分完成 | 自动刷新、重新规划剩余家具 | 禁用直到新预览绑定完成 |
| 完成 | 可重新分析 | 仅在新预览产生后再次启用 |
| 失败 | 可重试 | 禁用并显示安全失败原因 |

分析结果必须绑定以下摘要：

- 当前存档匿名身份与游戏日。
- House scene generation 与当前 build 身份。
- 当前全部房间身份、几何摘要和猫预计入住数量。
- 每个家具实例的身份、位置、方向、房间、属性和特殊效果摘要。
- 房间用途分配、家具到房间分配、空间布局和配置摘要。

玩家手动移动家具、切换存档、增减房间、购买家具、进入其他场景或 House
generation 改变后，旧摘要不再匹配，`自动放置` 必须保持零移动。

## 6. 分析与求解流程

### 6.1 捕获

1. 刷新运行时房间、猫与当前存档候选。
2. 读取全部家具，包括已放置、仓库、特殊家具和无法识别记录。
3. 读取家具效果、几何、旋转、锚点与房间可放置区域。
4. 读取现有猫房间计划，得到各角色预计人数和拥挤后的有效 Comfort。
5. 对未知家具或房间记录限制，但不让单个未知记录破坏其他可安全分析内容。

### 6.2 外层：房间用途与数量

外层规划器根据 `N`、猫群需求和可用家具生成角色数量候选。它需要允许角色重复，
并比较：

- 繁育组合池需要多少房间和位置。
- 战斗推荐成年猫、幼猫、恢复对象和普通猫的数量。
- 每个房间面积、锚点类型和放入家具后的可达属性。
- 创建专用房相对于合并用途是否真的提高整体最弱目标。

N 较小时优先合并用途；N 较大时只在有实际收益时拆分用途。

### 6.3 中层：家具分配

把家具分给房间时采用分层目标：

1. 特殊效果和安全硬限制。
2. 所有家具实例只能进入一个房间或留在仓库。
3. 最大化全部关键房间中的最弱目标，避免单项极高、另一项自动失败。
4. 最大化角色总收益。
5. 最小化不必要的跨房移动。
6. 最后处理全屋 Appeal 和装饰性收益。

玩家锁定、未知、任务相关或特殊家具默认保持原位。无法合法放置的家具留在仓库
并报告原因；不得出售、删除或静默丢失。

### 6.4 内层：空间布局

每个候选房间独立执行确定性布局：

1. 保留门口、通行区和不可用斜顶区域。
2. 先放置占地最大、旋转最少的大型 Solid 家具。
3. 再放置可提供 Anchor Point 的家具。
4. 再放置依赖 Anchor 的小件。
5. 最后放置墙面、天花板和 Background 家具。
6. 在同分方案中优先较少移动、较少旋转和稳定家具实例 ID。

求解必须有时间与节点预算。预算耗尽时返回当前已证明合法的最佳方案，并把未能
放置的家具列为限制，不能提交未经完整碰撞验证的布局。

## 7. 预览内容

F10 预览至少显示：

- 当前房间数量和识别到的全部房间。
- 每个房间的当前用途与建议用途。
- 当前属性、猫数量惩罚、预计有效属性和目标说明。
- 每件要移动家具的来源、目标、坐标/方向变化和移动原因。
- 保持原位、玩家锁定、未知和无法放置的家具数量。
- 特殊家具冲突，例如禁止繁育或提高打斗致死风险。
- 预计执行批次数和能否撤销。

布局尚未证明合法、原生执行能力未确认或存在关键未知数据时，只允许预览，不能
启用 `自动放置`。

## 8. 执行、取消与撤销

- UI 只提交已封存计划，不能直接写游戏状态。
- 新增 build-specific `FurniturePlacementGateway`，所有原生函数、偏移和对象
  布局只存在于适配器中。
- 执行前重新捕获完整家具与房间摘要；不一致即取消。
- 每个 UI tick 只执行小批家具移动，每件移动后独立读回位置和房间。
- 任何原生拒绝、场景变化、存档切换或结果不一致都会停止剩余批次。
- 分析时保存原始合法布局，执行成功后形成反向计划，供 F10 的一次性撤销使用。
- 撤销也要重新验证当前状态；玩家后续手动修改过布局时不能盲目覆盖。
- 不直接写活动 `.sav`，不修改 Steam Cloud，不删除家具。

## 9. 建议代码边界

以下只是新模块责任建议，不代表游戏 API 已确认：

- `snapshot/furniture_snapshot_*`：只读家具实例、库存和房间几何。
- `furniture_analysis/room_demand_*`：从猫规划计算动态角色需求。
- `furniture_planning/role_allocator_*`：动态 N 房间角色与数量规划。
- `furniture_planning/item_allocator_*`：家具到房间的属性优化。
- `furniture_planning/layout_solver_*`：碰撞、旋转和锚点布局。
- `workflow/furniture_workflow_*`：分析、封存、失效、分批执行和撤销。
- `execution/furniture_placement_gateway_*`：当前 build 原生适配器。
- `ui/furniture_analysis_*`：两个按钮和 F10 预览。

依赖方向保持：

`UI -> Workflow/Application -> Planning -> Snapshot/Game Adapter`。

求解器不能调用写适配器，执行器不能自行更改房间用途和评分规则。

## 10. 分阶段实施

### F01：家具与房间几何只读探针

- 已解码家具实例、仓库、坐标、Rare、完整 24x24 放置网格、`±1` scale 单元
  变换和房间基础碰撞网格；手动移动 `x/y` 持久化差分已通过，锚点语义仍待证据。
- 确认 1、2、3、4、5 房存档的动态发现方式。
- 输出匿名摘要；零写入。

### F02：开始分析按钮与分析快照

- 把右侧按钮改为 `开始分析`。
- 建立绑定存档、generation、房间、猫和家具的分析摘要。
- 仍不产生原生家具移动。

### F03：动态 N 房间规划和合法布局预览

- 覆盖 1–5 房与合成 N 大于 5 场景。
- 支持重复角色、合并用途、玩家锁定家具和无法放置报告。
- F10 显示完整预览；`自动放置` 仍保持禁用。

### F04：单件原生家具移动探针

- Stage 37 先用 F7 双快照采集一次玩家手动拿起、放置的运行时对象图变化。
- 根据 vtable RVA 与字段差分实现一个可恢复家具的原生拿起、放置和读回。
- 确认失败路径、场景生命周期和持久化行为。

### F05：自动放置、分批执行与撤销

- 左侧按钮改为 `自动放置`。
- 接通计划封存、执行前摘要比较、小批移动、停止和一次性撤销。

### F06：多房间玩家验证

- 分别验证 1、2、3、4、5 房真实存档。
- 额外用合成快照验证 N 大于 5，证明实现没有固定数组或四房分支。
- 每类存档验证分析零写入、预览一致、移动后属性读回、重复执行零移动和撤销。

每个阶段单独构建、测试、报告和本地提交，不预先实施后续阶段。

## 11. 最低验收条件

- 未点击 `开始分析` 时，不读取或求解家具计划。
- `开始分析` 对游戏状态和存档产生零写入。
- 1、2、3、4、5 房都使用相同动态集合接口，不存在固定四元素数组或只覆盖四个
  已知房间 ID 的执行逻辑。
- N 大于 5 的合成测试能够产生确定性计划。
- 相同输入重复分析得到完全相同的用途、家具分配和布局。
- 所有已计划家具无碰撞、锚点合法、方向合法、门口和禁放区域未被占用。
- 繁育房不包含 BreedSuppression；默认安全房不包含 FightRisk 特殊效果。
- 未识别、玩家锁定或无法放置的家具不移动、不删除，并有明确原因。
- 预览后任意家具、房间、存档或 generation 变化都会阻止执行。
- 执行后重新读取的房间属性和家具位置必须与预览一致。
- 重复执行稳定布局时提交零次移动。
- 任一验收失败时停止该阶段，不部署、不声称功能完成。
