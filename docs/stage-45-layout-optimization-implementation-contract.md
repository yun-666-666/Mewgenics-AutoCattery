# Stage 45 v0.5.42 房间布局重新优化实现合同

## 1. 文档地位

本文档是 Stage 45 剩余家具布局工作的约束性实现合同。后续代码、测试、真实存档
探针、构建、部署和阶段报告都必须服从本文档；除非玩家明确修改范围，否则不得临时
退回旧策略、改换目标、扩大阶段或用较弱结果替代验收条件。

本合同从当前未提交工作树继续，不重新实现已经完成的仓库家具创建、属性替换、失败
回收、批次回滚、运行时房间覆盖和 Support 审计链路。

## 2. 玩家要求与完成定义

本轮必须同时解决以下玩家可见问题：

1. 分析器不能因为阁楼当前布局合法，就把阁楼所有家具固定在原坐标。
2. 阁楼现有家具必须能够重新排列、压紧和为更优家具腾出空间。
3. 玩家以前手动摆放、属性已经过时的家具不能永久占坑；它们必须重新参与评分、
   重排和替换比较。
4. 仓库家具和其他尚未锁定房间中的优质家具必须能够进入目标房候选。
5. 当前存档 `Floor1_Small` 中四尊无负面单属性 `+5` 雕像必须参与阁楼候选：
   `special_stimulationidol`、`special_evolutionidol`、
   `special_comfortidol`、`special_appealidol`。
6. 一个房间只有完整但 `0 moves` 的方案时，不得阻断后续房间搜索，也不得被当作
   已优化完成并自动锁定。
7. 退出再进入家具模式不应使分析器因为清空会话锁而无限重复选择同一个零移动房间。

Stage 45 的布局部分只有在 day 339 真实存档只读探针生成一个真实、非零、可执行且
保持整屋 Support 全部合法的优化批次后，才算达到代码验收门。

## 4. 正式布局语义

### 4.1 目标房

- 目标房当前家具是必须重新评估的初始状态，不是固定障碍。
- 目标房已有家具可以改变坐标、改变组合位置和参与局部压紧。
- 目标房已有家具可以与仓库或未锁定房间候选比较属性收益。
- 不得以“玩家手动摆放”为理由自动永久保护其坐标或评分地位。
- 暂不新增未经验证的“任意已摆家具自动收回仓库”原生能力；若当前可靠执行器只支持
  房间内/跨房移动，则本批布局必须在该能力边界内生成。

### 4.2 来源房与锁定房

- 尚未锁定的其他房间允许提供优质候选。
- 调走家具后，来源房最终 Support 必须仍然全部合法。
- 已经成功自动优化并由刷新后的运行时状态确认的房间，在同一家具模式会话中锁定。
- 锁定房间中的家具不得被后续目标房拆走、暂存或当作候选。
- `0 moves`、执行失败、回滚、只完成分析或只存在属性替换，都不能把布局目标房标记为
  “布局完成并锁定”。

### 4.3 仓库

- 仓库家具继续参与候选。
- 仓库件只有进入最终计划时才生成原生 scene piece。
- 创建、校验、提交或后续批次失败时，继续使用已有回收和逆序回滚链路。

## 5. 阁楼评分规则

所有硬合法性和可执行性条件通过后，阁楼候选按以下优先级比较：

1. 四项核心属性最低值：Comfort、Stimulation、Health、Evolution；
2. 四项核心属性总和；
3. Appeal；
4. 成功纳入的有益家具数量；
5. 布局紧凑度和几何填充；
6. 更少的执行移动数作为同分稳定项；
7. stable key 作为最终确定性排序项。

含任一核心负值的 incoming 家具不得为了填空进入平衡阁楼。核心 `+5` 雕像的当前
调入优先顺序为：

1. key 265，Stimulation `+5`；
2. key 283，Evolution `+5`；
3. key 321，Comfort `+5`；
4. key 145，Appeal `+5`。

这个顺序用于限制局部搜索和提供确定性，不允许绕过实际属性比较或几何/Support
合法性。

## 6. 求解算法边界

### 6.1 必须采用的方向

从目标房当前 `Support` 合法布局出发，进行可执行的小批局部改进，而不是把所有家具
一次性清空后重新装箱：

1. 构建目标房和候选来源房的家具支撑依赖图。
2. 将共享支撑关系的家具划分为连通组件。
3. 每次只选择一个独立家具或一个有界局部组件作为可移动集合，其余家具保持为静态
   占用。
4. 对局部组件生成更紧凑的合法目标坐标；必须能转换成执行器可按顺序完成的移动列表。
5. 搬离时先移动最上层依赖，再移动底座；安装时先底座，再恢复上层依赖。
6. 每一步移动后，当前场景中的所有剩余家具 Support 都必须合法。
7. 局部压紧成功后，尝试在释放出的合法位置调入一尊优先雕像。
8. 若本批只能产生真实压紧而暂时不能调入雕像，可以返回非零压紧批次；下一次分析
   必须基于刷新后的布局继续尝试调入。

### 6.2 不得继续使用的失败方向

后续实现必须删除或合并现有重复实验分支，不得继续叠加：

- 把目标房现有家具全部固定，只向现有空洞塞家具；
- 对每尊 incoming 递归调用完整 `PlanWholeHouse`；
- 把跨房家具伪装成仓库家具后再改写 move 来源；
- 同时保留多套等价的 `single_incoming`、`target_without_optional`、
  `required_items + incoming` 回退；
- 为了产生移动而输出属性更差、Support 不完整或无法按顺序执行的布局；
- 仅以最终静态 Support 合法替代逐步执行合法性；
- 把第一个完整 `0 moves` 候选直接作为房间结果返回。

### 6.3 搜索上限

- 局部组件大小、候选坐标数量和 beam 宽度必须有确定性上限。
- 坐标上限必须覆盖目标房全部几何合法原点；候选生成不得只检查 row-major 前缀，
  也不得偏向旧截图中的左侧、右侧或任何固定区域。
- day 339 单次布局探针应恢复到适合玩家等待的有界时间；不得使用造成约 70 秒以上
  重复递归的路径作为正式算法。
- 若一个组件在上限内找不到改进，继续尝试下一个组件或下一个房间，不得把搜索失败
  误报为“房间已完成”。

## 7. Support 与执行硬门

任何返回给 UI 的布局计划必须同时通过以下条件：

1. 当前整屋 Support 合法。
2. 每个来源房在移出候选后的最终 Support 合法。
3. 目标房最终 Support 合法。
4. 整屋最终 Support 数量保持全部合法；day 339 必须保持最新输入快照的全部合法
   Support，不得使用旧快照的固定总数代替当前基线。
5. 生成的移动顺序可以被现有 `FurniturePlacementGateway` 逐 tick 执行。
6. 任一步不得临时拆掉仍在支撑未移动家具的底座。
7. 仓库件仅在依赖底座已经存在时创建。
8. 计划中的同一个 stable key 可以因安全暂存出现多次移动，但最后一次目标必须与最终
   审计一致，回滚仍按已提交 move 逆序执行。

任一条件失败，拒绝该候选并继续搜索；不得向 UI 暴露危险计划。

## 8. 必须补齐的自动化回归

`tests/furniture_layout_solver_tests.cpp` 至少覆盖：

1. 目标房已有家具可以离开原坐标并形成更紧凑布局。
2. 目标房已有家具不是永久固定障碍，incoming 可以使用重新排列后释放的空间。
3. 未锁定来源房中的无负面 `+5` 雕像能够进入阁楼最终计划。
4. 调走来源家具后，来源房其余家具 Support 仍合法。
5. 锁定来源房家具绝不进入候选和移动列表。
6. 第一个房间只有 `0 moves` 时，求解器继续找到后续真正有移动的房间。
7. `0 moves` 房间不会被布局完成逻辑错误锁定。
8. 核心负值 incoming 不进入平衡阁楼。
9. 同一输入重复分析产生确定性相同计划。
10. 最终整屋 Support 全部合法。

`tests/furniture_analysis_service_tests.cpp` 至少覆盖：

- 属性替换后的虚拟 stable key 与布局计划一致；
- 锁定房间列表正确传给布局器；
- 只存在属性替换时自动放置仍可用；
- 零移动布局不会阻断下一房间或被误报为完成。

## 9. day 339 真实存档验收门

使用现有只读 `furniture_geometry_probe` 和已确认房间尺寸。最终通过条件：

- `moves > 0`；

- 当前与计划最终 Support 都必须全数合法且 `unsupported=0`；对 2026-08-12 20:04
  快照当前基线为 `177/177`，若玩家再次保存则使用重新读取的最新全数合法基线；
- 计划中存在真实的阁楼坐标变化，而不是只重写相同坐标；
- 至少一尊应调入的 `+5` 雕像进入计划；如果第一批仅做局部压紧，则必须用确定的
  几何/依赖证据说明本批为何不能同时调入，并证明刷新后的下一批能够继续搜索；
- `evacuation_blocked=0` 且 `installation_blocked=0`；
- 再次对模拟后的布局分析时，不重复返回同一批，也不回到 `moves=0` 阁楼循环。

在以上条件未满足前，不部署 DLL，不把 v0.5.42 标记完成，不创建完成提交。
