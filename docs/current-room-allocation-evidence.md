# 当前房间分配证据与取舍

更新日期：2026-08-01

本文记录 `current-build-property-aware-cat-allocation-v3` 的事实边界。外部研究报告和
`All7Cat_ManualRoomAllocator` 只作为候选设计，不作为游戏字段、阈值或 API
的权威来源。

## 证据优先级

1. 当前仓库代码和当前 build 适配器。
2. 最新运行日志与玩家实机结果。
3. 当前存档的只读解析结果。
4. 可追溯的公开机制资料。
5. 用户提供的研究报告和算法骨架。

## 当前已确认

- 自动整理只由 House 按钮触发；不绑定每日、读档或结束一天事件。
- 当前 build 已验证普通房间 ID 为 `Attic`、`Floor1_Large`、
  `Floor1_Small`、`Floor2_Large`。
- 当前原生移动函数可移动猫并独立读回目标房间；8 猫与 25 猫两房存档已
  通过玩家验证。
- 存档能读取当前 House CatId、房间成员、七项属性和当前样本的公母。
- 公开 House 机制资料称：每个房间超过 4 只猫后，每多一只会使舒适度减
  1；这是一项属性惩罚，不是已证实的硬容量。
- Appeal 是全屋属性；Comfort、Stimulation、Health、Mutation 是房间属性。
- 当前存档 `furniture` 表已确认保存家具 ID 和所属房间；当前安装包的
  `resources.gpak/data/furniture_effects.gon` 保存家具的实际属性值。
- 主存档实读：`Attic` 刺激 41；`Floor1_Large` 变异 20；
  `Floor1_Small` 舒适 12；`Floor2_Large` 刺激 9、舒适 1。
- 25 猫三房档实读：只有 `Floor1_Large` 有非零培养属性（舒适 8、刺激 4、
  健康 2、变异 1），其余两房为 0。
- 公开 House 资料称亲缘、性向和 libido 等查看能力随 Tink 奖励解锁，不能
  假设所有进度都能读取。

## 当前拒绝或保持未知

- 不把 `default_soft_capacity=4` 当作游戏硬容量。
- 不使用文档给出的固定 A-E 房间用途。
- 不使用未验证的舒适、刺激、健康、变异阈值和角色权重。
- 不使用当前存档尚未可靠提供的亲缘、性向、libido 或家具阻止繁育状态。
- 不实现每日自动运行、强制繁殖、结束一天、直接生成猫、自动放生或删除。
- 不声称当前分配已经锁定实际配对或保证繁殖结果。

## 本轮已实现

- 对当前实际识别的 2、3、4 房计算均衡人数，目标人数最大相差 1；固定居民
  以后接回时可作为下限。
- 在已知公母数量足够且目标房至少 2 只时，每房至少放置一公一母。
- 人数仍保持最大相差 1；出现余数时，比较入住后舒适度并由实际属性决定
  哪个房间多一只，而不是固定房间顺序或沿用当前摆放。
- 高潜力猫优先进入刺激、舒适、健康更适合培养的房间；变异属性作为后续
  同分依据，不把 Appeal 误当房间属性。
- 具体猫的目标由潜力/战斗评分、房间用途和稳定 CatId 决定，不再以当前位置
  作为最少移动成本；人数相同但手动换猫也会恢复属性目标。
- 未知容量不产生淘汰建议，真实淘汰继续禁用；原生移动门仍负责最终拒绝。

## 尚未实现

- 在 House UI 中直接显示读取到的房间属性和逐猫目标原因。
- 可靠的亲缘、性向、libido、繁育兼容性和配对评分。
- 固定房间、NoMove、白名单与当前实时移动的完整接回。
- 详细逐猫预览、3/4 房玩家执行验证和保存后持久化验证。
