# 第 06 阶段：高评分战斗猫评分器与排序器

## 文档定位

实现单猫独立评分、资格过滤和排名。明确不做队伍搭配。


## 给 Codex 的通用执行规则

1. **只实施本文档对应的阶段**，不得提前实现后续阶段，也不得把多个阶段合并为一次大改动。
2. 开始前先检查当前仓库实际状态、已有提交、构建方式和本阶段依赖是否已完成；已有实现优先复用，不重复造轮子。
3. 不进行新的联网研究，不搜索新的 MOD，不擅自改换技术路线。本文档中的外部项目只作为既定参考基线。
4. 不修改游戏原始文件，不提交游戏二进制、反编译产物、个人存档、第三方闭源资产或未经许可的代码。
5. 每个阶段都必须：先读取相关文件 → 做最小修改 → 构建/测试 → 记录结果 → 创建一个本地 Git commit。**绝不自动 push 到 GitHub。**

7. 任何会移动、淘汰或写入猫数据的功能，默认必须可预览、可取消、可回滚；无法确认安全时只能进入只读模式。
8. 本阶段验收未通过时停止，不继续下一阶段。输出实际改动文件、测试结果、剩余风险和本地 commit 哈希。


## 固定技术基线

- 主路线：Windows x64 原生 DLL MOD。
- 运行时加载器：**Mewjector**。
- 游戏内 UI：**MewUI API**，以源码依赖方式编译进本 MOD。
- 可选安装管理器：Mewtator，仅用于安装和启停，不属于硬依赖。
- 参考实现：
  - Quick-Cleanup：参考“家园场景注入按钮并触发一次性操作”。
  - Mewgenics Breeding Manager：参考猫评分、血缘/近亲检查、房间优化、文件竞态处理；只能复用许可证允许的代码。
  - Online Savegame Editor：参考 `.sav` 解析、SQLite/LZ4、dirty tracking、备份和安全写回。
  - Mewgenics QoL Manager：仅参考批量筛选、房间移动、符号标记的交互思路。
  - MewgenicsModTool：仅作为“实时读取、推荐、cull 可行”的能力证据；未获许可时不得复制代码或资源。
- 不采用“自动组队策略”。战斗猫只按独立评分排序和标记，不分析职业搭配、站位或队伍协同。
- 两个主动按钮：
  1. 家园界面：`自动整理猫舍`。只有玩家点击后才分析、分类、淘汰和调整房间。
  2. 次日出征/选猫界面：`标记推荐战斗猫`。点击后只高亮高评分猫，不自动选队。

## 功能定义

输出“哪些猫自身战斗评分高”，而不是“哪四只猫组合最合理”。评分器必须确定性、可配置、可解释。

## 资格过滤

默认排除：

- 死亡、幼猫、明确不可出战。
- 当前被游戏状态标为不可用。
- 数据严重缺失且无法计算最低可信评分。

受伤猫是否排除由配置决定。繁育猫可以同时拥有战斗评分；分类冲突在第 7、9 阶段解决。

## 推荐评分模型

```text
CombatScore = StatScore
            + AbilityScore
            + PassiveScore
            + MutationScore
            + ClassBonus
            + AvailabilityBonus
            - DisorderPenalty
            - InjuryPenalty
            - MissingDataPenalty
```

不在代码里写死游戏平衡结论。所有权重进入配置：

```json
{
  "combat_scoring": {
    "version": 1,
    "recommended_count": 8,
    "minimum_score": 0.0,
    "exclude_kittens": true,
    "exclude_injured": false,
    "stat_weights": {
      "strength": 1.0,
      "dexterity": 1.0,
      "constitution": 1.0,
      "intelligence": 1.0,

    "ability_count_weight": 2.0,
    "passive_count_weight": 1.5,
```

## 归一化

为避免某个字段量纲压倒其他字段，支持：

- `raw`：直接加权。
- `min_max_within_house`：按当前猫舍归一化。
- `fixed_range`：按配置范围归一化。

默认先使用 `raw`，因为最可解释；后续可由用户切换。算法版本必须写入推荐快照。

## 数据结构

```cpp
struct ScoreComponent {
    std::string key;
    double raw_value;
    double weight;
    double contribution;
    std::string explanation;
};

struct CombatScoreResult {
    CatId cat_id;
    bool eligible;
    double score;
    double confidence; // 0..1
    std::vector<std::string> exclusion_reasons;
    std::vector<ScoreComponent> components;
};

struct CombatRanking {
    uint64_t source_snapshot_id;
    int game_day;
    std::string algorithm_version;
    std::vector<CombatScoreResult> ranked;
};
```

## 排序规则

1. eligible 优先。
2. score 降序。
3. confidence 降序。
4. 基础属性总和降序。
5. stable CatId 升序，保证完全确定。

推荐集合：满足资格和最低分后取前 `recommended_count`。不足则全部标记；超过时其余仍保留排名但不高亮。

## 解释输出

预览面板至少显示：排名、猫名、总分、数据置信度、前三个加分项、前三个扣分项。不得只给神秘总分。

## 缓存

评分只对快照运行。缓存键为：`snapshot_id + algorithm_version + config_hash`。配置改变立即失效。

## 测试

- 所有属性相同，按稳定 ID 决胜。
- 某猫字段缺失。
- 负权重、零权重、非法 NaN/Infinity 配置。
- 推荐数量大于合格猫数量。
- 1000 只猫评分在可接受时间内完成。
- 同输入重复 100 次结果完全一致。
- 验证代码中不存在职业组合/队伍协同逻辑。

## 验收标准

- 只读快照可生成稳定排名。
- 每只猫可查看分项解释。
- `recommended_count` 和阈值可配置。
- 不修改猫、不标记 UI；UI 接入在第 12 阶段。
